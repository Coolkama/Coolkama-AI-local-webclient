# Tight Arse AI

A standalone, mobile-first, free-tier-first LLM chat and web-search client built as a **single client-side HTML file**. The existing GitHub repository retains its original `Coolkama-AI-local-webclient` name. It can be opened locally or served as a **static webpage**. It is **not part of** the separate PC-hosted Coolkama AI ecosystem.

> **Project requirements:** [Scope and guardrails](docs/PROJECT_SCOPE.md). Read these before making changes.

## Inline generated visuals, without attachment-style cards (build v21)

Generated Mermaid diagrams and AI Horde images now appear **within the assistant's Markdown answer**, instead of being unconditionally appended after the answer text. Once a visual tool succeeds, the LLM is instructed to put an unambiguous standalone `[[diagram]]` or `[[image]]` placement marker at its intended location in its final response. The browser replaces that marker with the actual rendered visual; the marker is not displayed, copied or spoken. It is ignored if the matching media does not exist, and duplicates are suppressed. Markers inside fenced code are not treated as layout instructions.

For **existing saved chats**, or free models that omit a placement marker, the client chooses a reasonable fallback: directly before a paragraph referring to the diagram/image *above*, after one referring to it *below*, or after the introductory paragraph. This is a display-only change to existing content and does not require regenerating old answers or spending inference tokens. The user may still inspect editable Mermaid source and request revisions as before. Both a diagram and an image can have independent placement in one assistant reply when supported.

**Visual presentation is simpler:** The diagram or generated picture is shown directly within the answer, with no permanent title card, background label, row of download buttons or source information panel. Tapping the visual opens its full-size version. A small three-dot icon on the visual opens the existing actions: SVG/PNG/Mermaid source downloads and editable-source viewing for diagrams, or image download/open-original and provider metadata for AI Horde. White Mermaid backgrounds and independently styled nodes remain intact. AI Horde progress, cancellation and one-time privacy consent remain available at the image's inline position. The surrounding chat message's Copy/Speak/Retry actions remain below the entire reply.

The attached full diagnostics file for the observed unsolicited diagram confirms that the model called `create_diagram` before composing its final answer, which referred to the diagram as already above the text; the previous client appended it at the bottom regardless. It also had to correct invalid Mermaid syntax twice before successful rendering. Model decisions to create optional diagrams remain unchanged in this version; this release only changes layout and visual chrome. Browser rendering still requires live Android Chrome verification.

## Groq 413 oversized-input and mobile table fixes (build v19)

On 5 November 2026, an Android Chrome screenshot showed Groq returning **HTTP 413** (*request too large for model*) with an observed **8,000 token-per-minute ceiling** and **8,268 requested tokens**. Our earlier rolling context targeted **8,192 estimated input tokens**, leaving almost no margin for provider tokenisation differences, system/tool overhead and other free-tier limits. This is different from transient Groq HTTP **429** rate limiting; simply waiting cannot solve an individual oversized request.

For free **Groq** requests, v19 now imposes a **6,000-estimated-token effective input ceiling**, even if the saved Settings selector is higher, leaving a safety margin without deleting or rewriting locally stored conversations. The rolling context still keeps recent user turns and matched tool-call/result structures where possible, trimming oversized older evidence. Other providers retain their chosen input context. The Settings note explains the effective Groq ceiling. If a Groq request still gets an oversized-input `413`, the browser will **shrink that request once more** (approximately 3,800 estimated tokens or less) and retry once, with a diagnostic event `groq-oversized-context-retry`. This reattempt uses the ordinary conservative free-use counter. If the request still cannot fit, the error remains visible. HTTP `429` continues to use the separate bounded retry/wait policy.

The screenshot also showed a two-column factual Markdown profile table with its value column hidden beyond the mobile screen. At phone widths (up to 680px), two-column answer tables now wrap long text within the available width, showing both labels and values. Tables with three or more columns retain horizontal scrolling.

Code syntax checks, rolling-context tests with multiple 18K-character tool results, and a simulated Groq 413 reduction-and-retry all passed. Android Chrome rendering and live Groq response handling still require testing.

## Research-loop and Groq millisecond rate-limit fixes (build v18)

A 5 November 2026 conversation diagnostic exposed a failure on a follow-up about a Michigan public-health doctor. A normal greeting and two manual Retry clicks worked, then web research successfully found and opened results. A later research question used **three Tavily searches and three unique page opens** but continued issuing extra `web_open` calls for already cached pages after that budget had been consumed. The accumulated tool history grew to the configured ~8K input-context budget, caused repeated Groq token-per-minute `429` responses, and ultimately failed without a final answer.

**Mitigations:**
- When both the current turn's permitted searches and unique page opens are exhausted, stop advertising the exhausted `web_search` and `web_open` functions. The next model call can still request browser-owned `create_diagram` or `generate_image`, so a researched diagram or image is possible. Following that opportunity, send a *final-only* model request with `tool_choice:"none"`. This prevents endless cached-page reopens while retaining unchanged tools during ordinary research rounds. The underlying Tavily free-usage counters and maxima are unchanged.
- Groq sometimes returns fractional **milliseconds** in its rate-limit message (e.g. `Please try again in 899.999999ms`). The rate-limit parser now understands milliseconds and combined units rather than treating this as an unparseable error. It still uses bounded automatic waits/retries, never upgrades to a paid plan/model, and obeys local caps.
- If Groq still exhausts its allowance after retrieving web evidence, preserve the **retrieved source links** as an explicitly incomplete answer rather than replacing the entire reply with a bare error. Source links are not claimed to be a verified generated summary.

The parser and dispatcher have been syntax/unit checked, but this specific multi-round Android/Groq end-to-end scenario must be exercised in the live app to confirm timing and response quality.

## Assistant reply actions — Copy, Speak, Retry (build v16)

Each assistant reply now has a compact **three-icon action bar immediately beneath its chat bubble** (including older messages, generated diagrams and image replies):

- **Copy:** copies the full raw Markdown reply to the system clipboard (including code fences). When the reply contains a Mermaid diagram, its editable Mermaid source is appended. Uses the browser Clipboard API with a fallback and briefly displays *Copied*.
- **Speak / Stop:** reads the answer aloud through the browser's built-in `speechSynthesis` service, with no additional LLM request, paid text-to-speech API or key. Markdown is converted to readable text; fenced code blocks are announced but skipped. Longer replies are spoken in short chunks to improve mobile compatibility, and the icon changes to Stop while speaking. Speech stops when the user taps Stop, switches conversations, sends/retries another request or leaves the app. Voice availability, accent, reliability and whether a browser voice uses remote facilities depend on the device/browser.
- **Retry:** regenerates using the **original preceding user message and its selected attachments** with current free-model/search settings; it is a fresh, quota-counted model request, not a continuation of the previous answer. The newest reply is replaced within the chat; retrying an older reply creates a separate `Retry · …` conversation containing the history up to that user request, preserving the original conversation and its later messages. Tool support (Mermaid, AI Horde and web search) remains available under the existing free-only/consent restrictions. Replies sent through the manual AI Horde mode retry directly through AI Horde without paying an unnecessary model request. Shared browser-stored images are retained while any chat branch still references them.

Actions are disabled where appropriate while a model response is generating or another operation is running. The compact 36px buttons are accessible via labels/tooltips. No new application mode, backend, subscription or remote speech service is required. Actual Android Chrome speech and Retry flow should be tested live; unit/syntax checks alone do not establish browser compatibility.

## Diagram backgrounds and themes (build v15)

The **in-chat Mermaid diagram preview now defaults to a white canvas** with Mermaid's readable default light theme, independently of the Matrix-green app interface. The `create_diagram` tool accepts optional `background` (CSS colour name, `#RGB`, `#RRGGBB`, `rgb(...)`, or `transparent`) and `theme` (`default`, `neutral`, or `dark`). For example, asking for a dark-green canvas sets `background:"darkgreen"` and defaults to a dark theme; asking to make the background white sets `background:"white"` and uses a light theme unless the model explicitly overrides it. **Node colours continue to be controlled by Mermaid source** independently of the canvas.

The canvas colour is written into the sanitised SVG as a background rectangle (except when transparent), is used in the in-chat preview, and is applied to PNG downloads as well. SVG, PNG and chat preview therefore share the same intended background. Diagram code, title, background and theme are stored together in browser chat history and passed to the LLM on follow-up edits, so updating an individual node does not inadvertently reset the background. Older stored diagrams without style fields display on white by default. Different Mermaid themes are rendered sequentially to avoid cross-contamination from Mermaid's global configuration; the small SVG cache incorporates both the canvas colour and theme.

## Mermaid rendering fix (build v14)

The initial v13 diagram tool could produce repeated diagram-validation failures even with valid Mermaid source. The likely root cause is that this app uses Babel Standalone for JSX, which can transform `import()` into a browser-incompatible CommonJS `require()`. v14 loads a **version-pinned Mermaid 12.2.0 ES module using native browser import** outside Babel's transformation, then both parses the diagram and actually renders/sanitises its SVG before replying `accepted` to the model. Successful SVG is held in a small in-memory cache for the chat card to reuse.

A **Mermaid module-loading failure** now stops the turn immediately: repeated calls to the LLM cannot repair missing browser code, so it reports a specific error instead of wasting three validation attempts. The source supplied by the LLM is retained with a .mmd download option even if rendering is unavailable. Actual Mermaid syntax/rendering errors still allow up to three attempts, with diagnostics recording the original failure. Open **Diagnostics → Test Mermaid renderer** to load and render a tiny local Mermaid sample **without calling Groq, Gemini, OpenRouter or any paid service**. If that test succeeds but the model-created diagram fails, check the diagram-tool validation details or supplied Mermaid code. Browser end-to-end loading still needs confirmation on Android Chrome.

## AI-directed technical diagrams — Mermaid (build v13)

A tool-capable free chat model may now call browser-owned `create_diagram({code,title?})` whenever the user asks for a **diagram**, with no composer mode selection and **Web search switched off if desired**. The model supplies standard Mermaid diagrams-as-code (flowcharts, architecture, sequence, class, ER, state, timelines, Gantt and supported Mermaid types). The browser validates the tool arguments, imports the open-source Mermaid v12 ES module **on demand** from jsDelivr, checks Mermaid syntax locally and renders the diagram inside the same assistant message. The diagram source is **not uploaded to a diagram-rendering API**; jsDelivr only serves the generic Mermaid JavaScript library. CDN loading requires an internet connection unless the browser already has it cached.

Rendered diagrams appear with **Download SVG**, **PNG** and **Source (.mmd)** actions, plus a collapsible source preview. The rendered and sanitised SVG is displayed through an `<img>` using a local Blob URL; PNG export rasterises that same image in the browser. SVG/PNG may differ slightly in typography from the on-screen browser view. Source, not generated SVG markup or binary images, is persisted in the normal chat history, allowing refreshes and questions such as **“Add a cache between the API and database”** to pass the prior diagram back to the model for a complete revised `create_diagram` call. Existing conversations, image generation and Tavily web search remain separate and available.

**Safeguards:** diagram code is limited to 12,000 characters; model input may only specify `code` and an optional short `title`. Dangerous Mermaid configuration directives, link/click actions and callbacks are forbidden. Mermaid runs with `securityLevel:'strict'`, HTML labels disabled and bounded diagram size; SVG output is further sanitised before preview/export. At most **one valid diagram per user turn**, with up to three validation attempts. Invalid Mermaid syntax is returned to the model as a tool error so it can repair the diagram within the existing free inference budget. No AI Horde generation, paid diagram API, backend service, GitHub Actions or new server-side storage is involved. Not all free models support function calls reliably; the existing narrowly validated textual tool-call fallback also recognises `create_diagram` requests.

## Reliable image downloads (build v12)

The previous **Download image** button attempted a JavaScript `fetch()` from an AI Horde Cloudflare R2 image URL. Android Chrome could **open the image normally** but refused that cross-origin fetch (CORS), so the button displayed *Failed to fetch*. The existing **Open original** action works and is retained for older images.

New AI Horde image submissions now request `r2:false`, asking Horde to put **base64 WebP image bytes in the generation-status JSON** rather than returning an R2 link. The browser receives those bytes in the same already authorised API response, converts them to an image Blob, and stores them in its own **IndexedDB** (not in the small localStorage chat JSON). Chat history retains only the IndexedDB key; the image can be displayed again after reload while that browser storage is available. **Download image** now uses a regular browser `<a download>` link to a local Blob URL, not a cross-origin JavaScript fetch. The image is not uploaded to GitHub, and the browser chooses the download folder.

Previously generated R2-linked images **cannot be retroactively converted** to locally stored bytes without a CORS-enabled response. Their download action is instead labelled **Open image to save**, opening the already working remote original so the user can long-press/save in the browser. If Horde still returns a remote URL despite `r2:false`, the same fallback is used. If IndexedDB is disabled, the app falls back to an inline browser data URL with a warning about persistence; this can use more browser storage. Deleting a conversation also deletes its local generated image Blobs. The existing free caps, privacy consent and browser-only deployment are unchanged.

## Model-directed image generation (build v11)

Free, tool-capable chat models can now call the browser-owned `generate_image({prompt})` function **without selecting image mode or enabling web search**. The client validates the single 1–3,000-character prompt, limits model-triggered generation to **one image per user turn**, and returns an immediate small `accepted` / `consent_required` result to the model. The browser itself performs the asynchronous AI Horde submission, queue polling and final image display **inside the same assistant reply**; the model does not receive generated image pixels, and a second inference request is only needed if the model continues its textual answer. The normal image icon remains a direct manual shortcut.

Before the first model-directed image is sent to volunteer workers, the assistant reply displays a one-time privacy acknowledgement with the **exact proposed image prompt**. Selecting **I understand · Generate this image** saves the acknowledgement and generates from the browser without another model call. The consent screen explains the AI Horde anonymous-sharing override and LAION disclosure. Subsequent model tool calls may submit automatically while acknowledgement remains enabled in Settings. Neither the model nor an untrusted web page may bypass this consent. The same independent 2/minute and 20/day local image caps, 512/768 image sizes, 20 steps, one generated image per request and free-only policy remain in force.

Model tool calling depends on the selected free provider/model. Some free models refuse `tools`, or emit invalid textual requests; these errors are surfaced rather than invoking a paid fallback. The existing narrow Dots-style textual tool envelope is accepted for `generate_image` with strict argument validation. An in-progress image job keeps **Stop** connected while the model finishes any accompanying text; closing/reloading the browser interrupts the job and is marked as such in saved chat. A model cannot edit previously uploaded or generated images with this first text-to-image tool. No backend, paid model, additional CDN, or GitHub Actions workflow is introduced.

## AI Horde image generation (v10)

Click the **image icon** beside the globe in the chat composer to switch between ordinary text chat and **AI Horde text-to-image** generation. Enter a prompt and press Generate. Text models, web search and the user's existing provider selection are not involved in image requests. The app submits exactly **one** job to the official AI Horde endpoint and shows the queue position, approximate wait and generating state in the same assistant chat bubble. On completion it displays the image with **Download image** and **Open original** actions. Browser CORS may block a direct cross-origin download; use Open original and the browser's Save image option in that case. Remote image links can expire, so users should download images they want to keep.

**Anonymous by default:** No registration, key or payment is required. The public key `0000000000` is used when the optional personal AI Horde key is blank. Settings includes a personal-key field and 512×512 / 768×768 resolution selector. One image, 20 steps per request. AI Horde selects an available compatible model/volunteer worker; the user may get variable output quality and long waits. **No image editing or uploaded-image input** in the first release. Attachments must be sent through text chat instead. No paid models, credit purchases, automatic rerouting or paid fallbacks are introduced.

**Consent and privacy:** Image mode requires explicit acknowledgement. Prompts go to volunteer-run third-party workers; AI Horde's own API specification says anonymous image generations are **always shared with LAION**, even if the client sets `shared:false`. The original v10 request used `r2:true` (remote download links). As of v12 it uses `r2:false` (inline image bytes); `nsfw:false`, `censor_nsfw:true` and `shared:false` remain, with the anonymous-sharing override disclosed. Do not submit confidential prompts. Images may be worker-generated and vary in safety/quality.

**Free-only safeguards:** A separate local browser limit of **2 image submissions/minute and 20/day** applies; polls are not counted. The image request is made directly from the browser via `POST /api/v2/generate/async`, checks `GET /api/v2/generate/check/{id}` every 3 seconds, and gets the result only once via `GET /api/v2/generate/status/{id}`. A ten-minute queue timeout applies. Stop aborts requests and attempts `DELETE /api/v2/generate/status/{id}` when an ID was assigned. Pending generation cannot survive closing/suspending the browser tab. Free Kudos are queue-priority credits, not currency.

**Browser limits:** The API and image storage endpoints must permit cross-origin browser requests (CORS) for this static GitHub Pages site; a live browser request has not yet been independently verified with the selected environment. For returned Cloudflare R2 HTTPS image links, the client stores the link in the browser's chat history and displays a download action, but cannot guarantee that the remote URL stays live. An inline base64 response may consume substantial browser localStorage quota. The optional personal key is stored in browser localStorage, like the other provider keys, and is not encrypted.

## What it does

- Multiple saved chats, streamed model responses, Markdown/code highlighting and code snippet downloads.
- Free-only remote model selection, conservative browser-side usage limits, and optional local Ollama or offline test mode.
- Opt-in, model-driven web search: tool-capable LLMs can call a browser-owned Tavily Basic `web_search` function, receive sources and refine queries in the same turn (up to 3 searches per user message). Each search and each model round trip consumes the corresponding free-tier allowance and local counter. Models that do not support tools may reject web-enabled requests; no paid fallback is used.
- User-selected PDF, image, text and code-file attachments.
- Browser-local persistence for chats, settings and API keys.

## File access rules

**Users choose files to upload/process. Users can download generated outputs. The app must not edit, overwrite, delete, move or otherwise modify files already on their device.** File input is through browser-controlled selection, and saving is through normal browser downloads—not direct filesystem writes.

Selected content may be sent to the configured external AI provider when the user submits a request. When web search is enabled, model-generated queries (which may include conversation details) are also sent to Tavily. Files and chats are not automatically uploaded to GitHub. Browser localStorage is origin-specific, not a synchronised account, and API keys stored there are not encrypted.

## Running

Open `index.html` in a modern browser, or publish it with a static website host. CDN dependencies require internet access unless separately cached. Configure a supported free-tier provider key (or use the offline test mode); direct remote API calls and LAN Ollama access depend on the browser's CORS/network permissions.

Client-side rate counters are **not** a billing guarantee: use genuine free provider plans and provider-side billing protections. No paid model/search fallback is intended.

## Free image generation — AI Horde (build v10)

The single-file browser client includes **AI Horde text-to-image** as a separate mode in the message composer (image icon). No registration is required: the default API key is the documented anonymous key `0000000000`. Users may optionally enter their own free AI Horde API key under Settings → Image generation, and choose 512×512 or 768×768. Users must acknowledge that prompts and generated images are sent to community-run workers. Image mode does not send prompts to the configured chat model or Tavily.

The browser POSTs a single-image request to `https://aihorde.net/api/v2/generate/async`, checks the queue via `/generate/check/{id}`, retrieves the result once from `/generate/status/{id}`, and supports Stop via a best-effort DELETE. A ten-minute client wait limit and conservative local usage counter (2/minute, 20/day) avoid uncontrolled requests; they are not guaranteed upstream limits. Generated images appear in the chat with Download and Open original links. Image links can expire, and direct download may fail when the image host disallows CORS; Open original is the fallback. Browser suspension or closing the tab interrupts the operation. A successful API response and image display depend on external workers and the user's browser CORS policy, and have **not** been verified with a live anonymous generation in this development environment.

The original SVG splash, Matrix chat styling, existing text providers and their free-only safeguards remain unchanged. No backend, paid image provider, new CDN dependency or GitHub Actions workflow is required.

## Gemini model discovery (native API)

Gemini's **Discover FREE models** no longer relies only on the OpenAI-compatible `/v1beta/openai/models` response or matches against the three default dropdown entries. It calls Google's native `GET https://generativelanguage.googleapis.com/v1beta/models` with an `x-goog-api-key` header, follows `nextPageToken`, and converts native `models/gemini-…` names to chat-model IDs. The existing OpenAI-compatible `/chat/completions` endpoint remains unchanged for inference. If the native model-list request fails, discovery tries Google's documented OpenAI-compatible `/models` response as a fallback.

**Free-only constraint:** Availability in Google's model listing does **not** establish free-tier pricing. Only chat models independently verified as having free input and output pricing can be discovered: Gemini 3.8 Flash, 3.6 Flash, 3.5 Flash, 3.5 Flash-Lite and 3.1 Flash-Lite (subject to being returned by the user's API key). Native model records must support `generateContent`. Paid-only Pro, image, live/audio and embedding models are not enabled. Maintain the vetted list against Google's [pricing](https://ai.google.dev/gemini-api/docs/pricing) documentation rather than treating the API catalogue as a pricing authority.

Diagnostics now record the listing endpoint, page count, raw candidate count, number of eligible models and a sample of filtered model IDs (not the API key). If the API returns a model list but none qualify, the interface says so explicitly; the previous built-in suggestions or already discovered models remain untouched.

## Diagnostics (local-only)

Open **Diagnostics** using the activity icon in the navigation bar or **Settings → Open logs**. Recording defaults to **Normal**; use **Detailed** to see search queries, tool arguments and web results. **Full Trace** is opt-in and persists complete API request/response payloads in the browser's **IndexedDB**, including conversation text, uploaded document extracts, images, the Tavily response and raw SSE messages. The trace records model IDs (when reported by the provider), finish reasons, token usage (when provided), timings, errors and each inference/tool round.

**API keys and authentication values are not recorded.** Best-effort credential redaction is applied to all diagnostic levels; do not assume exports are free of other private data. Full traces can be large and use device storage. Log records are bounded to the latest 400 events, with a 650 KB compact metadata index in localStorage; IndexedDB holds large Full Trace payloads. Browser storage quota and eviction rules still apply.

**Save chat log** downloads records for the current conversation; **Save all logs** includes unrelated events such as model discovery. **Clear** removes both the compact index and full-trace database records. Logs are never automatically sent to GitHub or another service. Inspect JSON downloads before sharing them.

If diagnosing a search failure, enable Detailed or Full Trace, reproduce the question and save that conversation's log. Existing conversations are unaffected by changing diagnostic level; earlier events cannot retroactively acquire payloads.

## Research reliability and citation checks

- **Current date on every inference round:** the browser supplies the current local date/time, timezone and UTC time as a system message. This still works when `openrouter/free` intentionally selects a *different* free model for each request; model rotation is preserved.
- **Better search guidance:** the model is asked to search broadly before narrowing research, to prioritise credible dated sources, and not to mistake navigation snippets for actual articles.
- **Free Tavily Basic publication filtering:** queries about latest/recent news or research default to a `month` publication filter, while the tool may specify `day`, `week`, `month` or `year`. Explicit historical timeframes override the automatic filter. Evergreen cinema/showtimes and other live-listings queries are not publication-date-filtered. These options do **not** enable Tavily Advanced search or increase searches beyond the configured 1–3 per message.
- **Stable source references:** result IDs `[1]`, `[2]` etc. stay aligned with the combined retrieved-source list across repeated searches, with duplicated URLs merged. Publication dates appear where actually supplied by the search provider.
- **Citation URL audit:** completed web answers are checked against the URLs *actually retrieved* by the tool. Unknown numbered references and external URLs absent from retrieved evidence trigger a visible warning and diagnostic events. This is a provenance check, **not full fact-checking**, and does not imply that a linked article was opened or read in full.
- Full Trace records the injected date, search filter, tool-source map and citation audit, so future problematic replies can be investigated directly.

Suggested manual tests with Web enabled: ask for recent black-hole research, today's Liverpool cinema showtimes, a historical academic result from 2024, and an answer with citations. With Diagnostics → Full Trace enabled, inspect the requests for correct date awareness, recency filtering, stable source IDs and citation warnings. Provider behaviour remains variable because automatic free-model rotation is intentional.

## Streaming chat interface

- The composer has a compact, icon-only **globe** switch immediately beside the attachment paperclip. A highlighted globe means web search is enabled. It remains accessible via an on/off label and the settings panel.
- When the model requests web search, its assistant reply displays a **collapsed activity section above the answer**: **Searching web...** while Tavily is running, then **Searched web** when the current search completes. Expand it to see the queries and retrieved source links; neither is repeated below the answer. No search activity box appears if the model does not actually call web search.
- Chat **automatically follows streaming content only when the reader is near the bottom**. Scrolling up suspends follow, allowing the response to be read before generation finishes. Returning near the bottom re-enables follow, and the floating **Latest** button jumps back to the end. Sending a new message intentionally returns the view to the newest reply.
- These are interface changes only: provider selection (including OpenRouter's intentionally rotating free model), tool-call handling, usage safeguards and local diagnostics remain in place.

## Rotating-model tool compatibility and follow-up evidence

- OpenRouter's `openrouter/free` option **intentionally rotates models** between inference rounds. The workbench accepts OpenAI-compatible structured tool calls and additionally detects a narrow Dots-style textual `web_search` envelope. Textual requests are validated against the same search schema and per-message budget before execution.
- Streamed tool-markup prefixes are withheld from the visible answer. If a model requests another search after the budget is exhausted, or emits malformed markup, the reply is labelled **incomplete** and the existing source links are retained rather than showing hidden tool tags as an answer. No unverified summary is invented.
- Retrieved source titles, URLs and excerpts are passed back as untrusted evidence with subsequent conversation turns, allowing follow-ups such as **Summarise the information** to use already-fetched sources without immediately consuming another search credit.
- Before executing a model-requested Tavily search, the client checks that a free LLM continuation request remains available. Otherwise it presents the existing sources and does not waste a Tavily credit.
- No model pinning, hosted search, paid fallbacks or quota increases were introduced. Full Trace logs record recognised textual tool attempts and quota stops.

## Groq invalid-tool-call recovery

Groq-hosted tool-capable models may sometimes generate invalid function arguments after receiving valid web search results (for example, treating `web_search` as if it could open a result by `index`). Groq validates the tool schema and may report `tool_use_failed` inside an **HTTP 200 streaming response**. This is model-generated invalid tool use detected by Groq, not a Tavily failure.

When this happens **after sources have already been retrieved**, the workbench attempts **at most one** additional Groq inference request with `tool_choice: "none"`, asking the model to answer from those existing results. It first checks the local free-tier inference cap and spends **no additional Tavily search credits**. If the recovery fails, is blocked by the cap, or yields another tool call, the answer is marked incomplete and the retrieved source links remain available.

The workbench does not silently switch to a paid model, Groq hosted browser search, or another provider. OpenRouter's deliberately rotating Any Free Model option remains unaffected. These paths are recorded in Full Trace diagnostics.

**Rate-limit recovery:** if Groq rejects a later model request (for example, HTTP 429 for its tokens-per-minute allowance), any search results and opened-page extracts already attached to the failed assistant message remain usable as untrusted evidence on the next turn. The model can answer a follow-up such as “Summarise the previous results” without losing those sources. This does not raise or bypass Groq's provider rate limits, and the separate automatic Groq retry mechanism may wait for a reported rate-limit reset before resending a rejected request, subject to free-tier safeguards.

## Model-driven page opening (`web_open`)

When Web is enabled, a tool-capable model can now call either `web_search(query, time_range?)` **or** `web_open(index)`. `web_open` reads the 1-based numbered result returned by a search **in the current user turn**, using Tavily's **Basic Extract API**. This avoids the invalid `web_search({index: 2})` calls observed with Groq. Only URLs from actual search results may be opened; the model cannot make arbitrary URL-fetch requests. Previously opened pages are cached for the remainder of the turn, so reopening the same source doesn't spend another Tavily credit.

The model may make at most **three web searches and three new page opens per user turn** (search count remains configurable from one to three). Extracted page text is passed to the model up to 18,000 characters per open, and up to 12,000 characters per opened result is retained with the conversation for follow-ups; Full Trace logs include the raw Tavily extraction response. An open may fail or be incomplete for paywalled or dynamically generated pages. There is no automatic Advanced Extract or paid fallback.

**Free-only accounting:** Tavily's free Researcher plan gives 1,000 API credits/month. A Basic search costs one credit; Basic Extract costs one credit per five *successful* URL extractions. The app deliberately reserves a conservative **full local credit for every extract call**, including failures, and uses the existing combined 900-call-per-month browser counter for both searches and opens. Each model continuation separately consumes a free LLM request. Browser counters do not account for calls from other apps sharing the same provider key.

The collapsed **Searched web** panel displays search queries, opened pages and source links, including which sources were read. The normal/detailed/full local diagnostics record extraction timing, failures, the returned text (Full Trace) and cache hits. The tool schema is made available dynamically when the corresponding per-turn budget permits. Both OpenAI-compatible structured function calls and the supported Dots-style textual calls can request `web_open`; OpenRouter's Any Free Model rotation remains enabled.

## Per-request output length (Groq 16K; others Automatic by default)

- **Groq now defaults to Manual 16,384 output tokens per request**, sent as `max_completion_tokens: 16384` for the current Groq API. The same limit applies to its automatic continuation requests. Existing saved Groq profiles on Automatic mode migrate once to Manual 16K; deliberate existing Manual limits are kept unchanged. The user may change the limit or restore Automatic in Settings.
- OpenRouter, Gemini and Ollama still default to Automatic, which omits `max_tokens` and lets their respective model/provider choose the output allowance. Manual mode sends `max_tokens: N` for these providers.
- **Important free-tier constraint:** Groq lists GPT-OSS 20B/120B at **8,000 TPM** on the Free plan. A 16,384-token maximum is a requested ceiling, **not** permission to exceed throughput quotas or a guarantee of a 16K response. Groq may return a 429, wait, reject an oversized request, or stop earlier. The app retains bounded waits and local request caps; no paid fallback.
- Automatic continuation runs if `finish_reason: "length"` or an unclosed fenced-code block indicates an unfinished response. An ordinary `stop` does not trigger continuation just because the response used fewer than 16K tokens. The continuation alignment checker may reject restarted code rather than corrupting the original answer.

## Continue truncated answers in place

When a free model reaches its output-token allowance (`finish_reason: "length"`) or finishes with an unclosed Markdown code fence, the **last assistant response** is marked **Incomplete**. A **Continue writing** button appears beneath it. The button is also offered for some older stored answers that were previously marked Done but contain an unclosed code fence.

Each explicit button press makes a free-tier-capped LLM continuation request, with tools disabled and a strict continuation instruction. It appends the new text to the **existing assistant message** instead of creating another chat message. The start is buffered, repeated fences and suffix/prefix overlap are aligned before showing new text, and the answer stays incomplete if it reaches the limit again, leaves code unclosed, restarts an earlier code section or fails HTML/JavaScript syntax validation. An interrupted or failed continuation preserves the previous text. Up to **six manual continuations per answer** are permitted. The button is restricted to the latest assistant message to keep conversation history coherent.

Automatic continuation is enabled by default (see below), while **Continue writing** remains a manual fallback when generation stops incomplete. There is no billing fallback, additional Tavily usage or model pinning. Each manual continuation consumes the current provider's free inference allowance and may still hit provider token-per-minute or context limits. Exact character-perfect continuation is model-dependent; deterministic alignment cannot invent missing expressions or ensure semantic correctness. Full Trace records `continuation-start`, `continuation-finished` and failure/stop events.

## Rolling context window

Long conversations now use a **deterministic, rolling request context** instead of sending the entire saved history to the model every time. Only the API request is windowed; the complete chat, source links, attachments and partial answers remain in local browser storage. There are **no summarisation inference calls** and no additional Tavily requests.

In **Settings → Rolling context window**, select an approximate *input-token* budget per provider: 2,048, 3,072, 4,096, 8,192, 16,384, 32,768 or 65,536. Groq now defaults to **8,192 estimated input tokens** to preserve more of a growing codebase during long answers. Existing Groq profiles still at the old 3,072-token default are upgraded once; deliberately configured other windows remain unchanged, and users can choose 3,072 again. Output length is independently set to Automatic (provider decides) unless the user explicitly switches to Manual. Other providers default to 8,192 estimated input tokens. The client estimates input tokens conservatively from text length and approximates image cost; **it is not a model tokenizer**, doesn't know a rotating model's exact context size and cannot guarantee the provider's TPM limits.

The client always keeps the system instructions and current date, plus the most recent two conversational turns. If these exceed the selected budget, it shortens long excerpts (marking omitted spans). Older *complete* turns are included newest-first only while they fit, and omitted from the request once the budget is exhausted. The structure of model tool calls and their matching results is never separated; shortened tool results remain valid JSON where possible. Research links/indices are preferred over verbose excerpts. Every inference round—including web searches, Groq text-only recovery and explicit code continuation—is re-windowed from the locally retained source context.

When history is omitted or shortened, the chat response displays a small rolling-context indicator. Normal diagnostics emit `context-window` with the estimated input cost, budget, number of older messages/turns omitted and count of shortened excerpts. The original chat is never rewritten by this feature.

This is a **recency-based window, not semantic memory or LLM-generated summarisation**. Information from older dropped turns may be unavailable to the model unless the user restates it or asks to retrieve the sources. Request-token estimates, provider context limits and true token-per-minute consumption vary by model.

## Provider-specific continuation strategies (Groq GPT-OSS)

- A provider-specific continuation router now selects **assistant-message prefilling** for Groq `openai/gpt-oss-20b` and `openai/gpt-oss-120b`, when **GPT-OSS assistant prefilling** is enabled in Groq Settings (default on). The final API message is the **existing assistant response**, once, without an additional user `Continue` request or duplicated code. The model is asked to generate the suffix of that assistant message.
- Groq non-GPT-OSS models, OpenRouter, Gemini and Ollama retain the ordinary assistant-plus-user-follow-up protocol. Disabling Groq prefilling returns to that protocol. This is a capability-specific change, not an assumption that all providers expose identical continuation behaviour.
- For Groq prefilling the exact system/date/user/tool-request prefix of the prior inference round is reused unchanged when it fits the configured input budget; otherwise a conventional follow-up is used. Groq **automatically** caches matching prompt prefixes for supported GPT-OSS models; the app sends no session ID or separate caching API call. Cache hits are opportunistic, not guaranteed.
- Groq still enforces account-specific free-tier limits, output ceilings, and TPM/RPM/RPD quotas. Increasing the input context can increase 429 waits. The client still performs buffered suffix overlap alignment and final code validation; prefilling is not a guarantee of correct code. `auto-continuation-start` and `continuation-start` diagnostics include the selected protocol.
- Groq's API documents assistant prefilling, but we have **only run simulated regression tests** here, not a live free-key request. If your Groq model returns an incompatible-request error, disable prefilling under Groq Settings and export the diagnostics.

Official references: [Groq assistant prefilling](https://console.groq.com/docs/prefilling), [prompt caching](https://console.groq.com/docs/prompt-caching), [Groq rate limits](https://console.groq.com/docs/rate-limits).

## Reasoning-only streaming diagnostics

Certain OpenRouter free-router models (observed with `dots-studio/dots-3-note-preview:free`) can stream thousands of `delta.reasoning` / `reasoning_details` chunks before emitting any visible `delta.content`. This is **not** an inactive network request. The chat now shows a lightweight **Model reasoning** activity counter and the actual selected model name while waiting for the first visible answer. It never displays private reasoning text in the chat. The stream records total reasoning characters/chunks in `llm-round-end` diagnostics; Stop continues to abort the request immediately. Reasoning-heavy free models may take a long time or never produce a final response within the chosen timeout/allowance; no automatic paid switch is introduced.

The 3 November diagnostics also showed GPT-OSS 120B returning `finish_reason: length` after 3,072 total completion tokens on each request even though the client sent no `max_tokens`. This is **observed provider-chosen behaviour**, not evidence that the model supports no higher output limit. To experiment with larger single completions, select a positive **Manual output token limit** under Settings, keeping provider free-tier token budgets and rate limits in mind. No automatic output limit is silently imposed.

## Provider adapters, streaming metadata and caching integrity

- **Groq:** All web-enabled inference rounds in a single user answer advertise the *same* two Tavily Basic function schemas and `tool_choice: auto`. Browser-side search/open quotas remain enforced at execution. Cache-friendly GPT-OSS prefilling reuses the exact previous model request prefix and tool configuration; if the context budget cannot accommodate the prefix, it uses a normal assistant-plus-user continuation. The original prompt is not recreated or shortened in the prefill path. Cache tokens are read from the trailing SSE usage event when the provider emits them. `cachedTokens: null` means the API did not report a figure, not that a cache miss is proved.
- **Groq prefilling is experimental:** Models may still restart an HTML document even with a preserved prefix. Automatic completion can retry once using the ordinary follow-up protocol after a detected restart or incompatible prefill error, counting that *second* inference request toward both the free request counter and the **six total automatic continuation requests**. Manual **Continue writing** sends **one model request per press**; a misaligned result leaves the code intact and allows the next press to use normal follow-up. Manual continuations do not advertise Tavily tools.
- **Gemini:** Streamed function-call `extra_content.google.thought_signature` is retained on the original call and echoed with the assistant tool-call turn, before its corresponding tool results. Assistant-level Gemini extra metadata is retained in completed chats and replayed only to Gemini. This prevents losing provider-required opaque state while keeping the existing OpenAI-compatible endpoint.
- **OpenRouter:** Free fixed-model requests include a stable per-chat `session_id` for provider routing, plus `usage: { include: true }` for in-stream accounting. `openrouter/free` deliberately omits the sticky session routing key so it can continue rotating free models. Streamed `reasoning_details` blocks are preserved in order and returned intact with subsequent tool results and same-provider conversation turns.
- **Every provider:** The normal model API remains free-tier-only, and no paid fallback, hosted web tool, background service or user filesystem permission is added. Provider-controlled caching is opportunistic and these changes are not a guarantee of complete HTML or a cache hit. The client retains diagnostics for protocol choice, cache fields, failed boundaries and fallbacks.

## Seamless automatic completion and Groq rate-limit waiting

**Seamless long answers** is enabled by default and can be turned off under Settings. When a model response hits `finish_reason: "length"` or ends with an unclosed fenced-code block, the workbench automatically requests **only the missing suffix**, appends it to the **same assistant message**, and continues normal streaming without displaying a separate continuation message. Continuation starts are buffered and checked using exact suffix/prefix overlap up to 12,000 characters, duplicate-code-fence handling and restart/declaration guards; ambiguous starts are not displayed until aligned. Up to **six additional inference requests** may be made per answer, bounded by provider free-tier caps; no automatic paid provider switch, hosted tool, or Tavily search is triggered. If completion remains impossible, the saved answer is marked incomplete and the older manual Continue button remains available. The full trace records auto-continuation starts, completions and stops; normal chat UI does not expose individual continuation rounds.

Groq HTTP 429 / `rate_limit_exceeded` responses are handled with an **abortable wait-and-retry loop**, using `Retry-After`, Groq's “please try again in” message (including decimal seconds or minute/second combinations), or its token reset header. Retry waits add a short guard margin. The workbench makes at most **three rate-limit retries per inference call**, with **15 minutes maximum per provider-requested wait**; waits longer than this and daily exhaustion stop instead of trying indefinitely. The conservative local Groq per-minute counter may independently require waiting up to one minute, at most twice per request. **Every attempted request is counted**, including rejected 429 requests. During the wait the same assistant turn remains active, and **Stop** aborts the wait. If the browser tab is closed, reloaded, suspended by the phone, or loses connectivity, this browser-only application cannot guarantee the wait and automatic retry will finish.

**Continuation integrity:** For continuation rounds, a shortened previous assistant message now preserves the latest code tail rather than the older head. The previous code is included **once**, as an assistant message, not copied again into the user instruction. A generated fenced HTML document is checked for unclosed scripts, duplicate named functions and JavaScript syntax errors before the turn is marked Done. An invalid join or script is marked Incomplete with a visible explanation and diagnostic event; no automatic extra model-based repair calls are spent. This is a syntax safeguard, not a full application runtime/quality test. Small configured input windows may still omit earlier implementation detail.

Large input/output settings can cause a Groq request to exceed its limit on a *single request* (such as HTTP 413). That cannot be fixed by waiting and is not retried. Other providers' 429 responses are not automatically retried. Provider output length and model context remain subject to individual limits.
